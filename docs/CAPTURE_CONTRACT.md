# Android ↔ Windows capture contract, version 1

Each JSONL line is one event. Both platforms use:

\- `schema_version`: integer 1.

\- `type`: `session_start`, `raw_frame` or `session_end`.

\- `session_id`: a fresh UUID per capture.

\- `sequence`: increasing integer starting at 1, unique inside that session.

\- `device_model`: exactly `Elitech ANE-200W`.

\- `transport`: `bluetooth-le` for this initial prototype.

\- `device_id`: local device identifier, retained only in private captures.

\- `service_uuid`, `characteristic_uuid`: discovered identifiers of the selected source.

\- `received_at_utc`: timezone-qualified ISO timestamp generated by the capturing host.

\- `elapsed_ns`: monotonic elapsed time within the session; never compared as an absolute clock between hosts.

\- `decoder_status`: `unverified` for undecoded raw evidence, or `vendor-app-derived` for the current live profile. This is provenance, not a calibration certificate.

\- `payload_hex`: original bytes for raw-frame events; absent for lifecycle events.

\- `reason`: optional termination reason on a session-end event.

Receive timestamps are not device measurement timestamps. Packet sequence preserves arrival order; a disconnect/session-end must not be converted into a zero measurement. Unknown bytes do not become numeric readings. Android and Windows local clocks must be checked before comparing capture sessions.

Windows archives records by `(session_id, sequence)` and rejects a changed payload for an existing key. Reimporting identical evidence is idempotent. Imports run in a SQLite transaction; a conflicting event aborts the import.

The separate measurement CSV is an analysis input, not the BLE wire protocol. Required columns are `received_at_utc` and `velocity_mps`; optional columns are `temperature_c`, `humidity_percent`, `quality`, `source`. Quality is `valid`, `stale` or `error`. A missing velocity is accepted only for non-valid rows and remains missing. Imported readings are labeled imported/synthetic according to their source; they are never promoted to a live Bluetooth reading.

CFM outputs are derived from the input velocity, entered area and multiplier. Full calculation precision is retained; displayed decimals are separate. Sample means are explicitly arithmetic; time-weighted averages, stable-window rules and stored-meter retrieval require further implementation and validation. The current live profile is documented separately in PROTOCOL.md.

Single-reading saves use their own `single_reading` JSONL files, not the raw-event importer. Each contains a unique `reading_id`, original `received_at_utc`, `saved_at_utc`, `display_state` (`live` or `held`), canonical `velocity_mps`, converted `velocity_fpm`, `temperature_c`, `humidity_percent`, quality/source/protocol provenance, original `payload_hex`, session/sequence and an optional note. Phone/Windows saved-reading CSV export is compatible with the measurement CSV importer. Saving a held reading does not replace its receive timestamp with the save time.
